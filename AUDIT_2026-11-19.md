Local only: production build of the site (`.next-audit`, port 3100) against the local API (port 4000) with email and Stripe disabled. Nothing was deployed.

## Verified working (no change needed)

- Backend: 304 tests pass (incl. disposable-PostgreSQL inventory, checkout, rules, policies); live API integration test passes (auth, roles, CORS, cookie CSRF, validation, sanitising, uploads, rate-limit headers).
- Production build, lint and type checks clean. Dependencies: 0 known vulnerabilities (site and API, production dependencies).
- Rate limits on every public write (inquiries, checkout, quotes, staff and customer login, magic link, password reset, email change). Staff login locks after 4 bad attempts per minute, customer login after 8.
- Session cookies: HttpOnly, SameSite=Strict, Secure in production; customer writes require origin + CSRF header; unknown-email logins compare against a dummy hash.
- API latency (20 samples each): public endpoints p50 ~15 ms, p95 under 30 ms; heaviest admin view 46 ms p50.
- Human checks: contact form validation and submission, login errors (no account enumeration), all 13 admin sections, mobile menu, booking dialog, journal search and pagination, popups.
- Redirects 20/20, assets 8/8, browser smoke 0 issues, axe 0 violations on sampled routes.

## Not fixed, with reason

- **Mobile performance on image-led pages (56-68).** Root cause measured: the root layout loads 21 global stylesheets (~690 KB of CSS on a service page, ~900 KB of CSS source including large legacy layers such as `legacy-routes.css`, `design-system.css`, `classic.css`), producing ~2.3 s of style/layout work on Lighthouse's throttled phone. Real unthrottled loads are fast (coworking hero: 49 ms TTFB, 106 ms download). Safely removing unused CSS needs a dedicated consolidation with per-route visual regression. `experimental.inlineCss` was tested and rejected (pixel-identical but 1.7-2 MB HTML per page).
- **Production-only checks** remain outside local scope: real Stripe test-mode end-to-end, production SMTP/webhook/R2 configuration, the local migration-history divergence (`20261108000000_direct_payments`), and rotating the previously exposed R2 and Gmail credentials.
- Inventory enforcement at checkout is still off by default (`INVENTORY_CHECKOUT_ENFORCEMENT`) and the admin/customer booking interfaces for it are not built yet (see `WSJ_IMPLEMENTATION_PROGRESS.md`).
